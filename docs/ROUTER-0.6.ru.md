# Router 0.6: устойчивость AWG и резерв HY2

Основной транспорт — AWG. В режиме «Авто» повторяющиеся прикладные ошибки или
устойчиво медленные успешные запросы к двум независимым провайдерам переводят
трафик на резерв. Сначала проверяются HY2 группы сервера AWG, затем остальные
HY2, затем другие семейства. Ручной выбор профиля сохраняется: автоматической
подмены выбранного профиля нет. Если резервы не работают, VPN-трафик остаётся
закрыт; прямой WAN не становится резервом.

Группы нужно настроить явно. В «FLR → Настройки → Группа сервера основного AWG»
задайте, например, `main-server`. В «Профили» назначьте ту же группу HY2,
которые находятся на этом VPS. Имя должно совпадать точно. По endpoint AWG
соответствие автоматически не определяется. На чистой прошивке и при миграции
старой конфигурации пустая группа означает общий порядок HY2 по приоритету,
без гарантии «тот же сервер первым». Меньший числовой приоритет выше; группа
AWG среди HY2 имеет преимущество над числом. Все HY2 проверяются раньше других
семейств.

## Что измеряется

Раз в5 секунд запускаются HTTPS и UDP DNS к Cloudflare и Google: максимум
четыре запроса с общей границей4 секунды. HTTPS использует фиксированные
сокеты `104.16.124.96:443` и `8.8.8.8:443`, правильные TLS-имена и проверку
ответов; перенаправления запрещены. DNS идёт на `1.1.1.1:53` и `8.8.8.8:53`.
У профиля только с TCP запросов UDP нет, и поддержка UDP не появляется.

Это время полного успешного прикладного запроса, включая соединение/TLS и
чтение ответа для HTTPS, а не ICMP ping или измерение потерь пакетов. Сбои не
доказывают намеренное ограничение. Время всего раунда остаётся отдельным полем
`round_duration_ns`: таймаут одного провайдера не становится временем успешного
запроса второго. У каждого запроса есть время в миллисекундах;0 означает отсутствие
успешного измерения. Отказ или замедление только одного провайдера не даёт
решения о деградации сети.

## Предварительные настройки

Все настройки доступны в LuCI и через аутентифицированный `settings` API.
Полная схема, ограничения и пример JSON: [ROUTER-API.md](ROUTER-API.md).

| Настройка | По умолчанию | Допустимо |
| --- | --- | --- |
| Детектор устойчивых нарушений | включён | да/нет |
| Окно | 60 с | 30–300 с |
| Минимум наблюдений | 8 раундов | 6–60; не больше `окно/5 + 1` с округлением вниз |
| Ошибки каждого провайдера | 25% | 25–100% |
| Медленные запросы каждого провайдера одного протокола | 75% | 50–100% |
| Абсолютный порог TCP / UDP | 1500 / 400 мс | TCP500–3500; UDP100–2000 мс |
| Восстановление и допуск обучения TCP / UDP | 750 / 200 мс | TCP от100; UDP от25 мс; строго ниже соответствующего порога замедления |
| Множитель базового времени для замедления | 4 | 2–10 |
| Множитель для восстановления | 2 | от1, строго меньше множителя замедления |
| Обучение базы | 12 чистых раундов | 6–60 |
| Непрерывное восстановление | 60 с | 60–600 с |
| Максимальная пауза между проверками | 30 с | 10–60 с |

Ошибки считаются отдельно по каждому провайдеру внутри одного окна; они могут
произойти в разных раундах. При достижении доли каждым провайдером и как минимум
двух ошибочных раундов у каждого AWG деградирует. Для времени нужны медленные
успешные запросы того же протокола у обоих провайдеров. Один выброс не переключает.
Частые нажатия «Повторить проверки» не увеличивают число наблюдений: минимум
5 секунд между учитываемыми раундами. История ограничена фиксированным массивом,
не растёт и не сохраняется на диск.

База отдельная для каждого провайдера и протокола: верхняя медиана12 чистых
последовательных наблюдений. Все времена должны быть не больше750мс TCP и200мс
UDP; ошибки/медленные наблюдения должны выйти из окна. До готовности базы
действуют абсолютные пороги. Поэтому медленный канал при холодном старте не
обучается как нормальный. Готовая база фиксируется до изменения политики или
перезапуска; деградировавший путь не может повышать её.

Порог замедления — максимум абсолютного порога и базы ×4; медленный запрос
должен быть строго выше. Порог восстановления — максимум750/200мс и базы ×2;
запрос должен быть не выше него. Для возврата нужны оба протокола обоих
провайдеров: минимум13 чистых наблюдений за полные60 секунд. Ошибка, медленный
ответ, отсутствие времени или промежуток между проверками более30 секунд (настраивается)
начинают отсчёт заново. Одного быстрого ответа или логического «успешно»
недостаточно. Предел30 секунд учитывает известные задержки проб, запуска и
ограниченного ожидания остановки процессов. Даже при редких пробах нужны все13
чистых наблюдений, поэтому фактическое восстановление может занять больше60 секунд.
Изменение политики сбрасывает историю и квалификацию, но не делает
нездоровый канал здоровым. Отключение детектора сохраняет немедленный отказ при
исчезновении интерфейса, три полных сбоя подряд и квалификацию восстановления.

«Обзор» показывает причину, количество ошибок и медленных запросов каждого
провайдера, время последнего запроса, базу и ход восстановления. После деградации
очищаются старые AWG-соединения; при ошибке очистка повторяется, а переключение
на резерв ждёт её завершения. Защитные правила не снимаются. Существующие direct
SOCKS5, отдельное отключение VPN и явное принятие подключения после проверки
LAN/WAN сохраняются.

Поиск резервов делится на шаги с общим4-секундным контекстом запуска и проверок.
Следующий шаг продолжает порядок кандидатов, поэтому длинный список отказавших
профилей не заставляет начинать поиск с первого и не задерживает AWG на минуты
только из-за последовательных сетевых таймаутов. Жизнь уже выбранного процесса
не ограничена временем шага. Существующие синхронные native-команды настройки
фаервола/маршрутов, очистки слота и pin-маршрута пока не подчинены этому общему
контексту; остановка может ждать до5 секунд на процесс. Полная жёсткая граница
времени native-шага не заявляется. Такие задержки и реальные скорости запуска
движков нужно проверить на установленном роутере.

Пороги консервативные и предварительные. Раздельные границы UDP400/200мс позволяют
видеть устойчивую задержку DNS/игрового пути, которую TCP-порог1500мс пропустил бы.
Пригодность для конкретного ISP, полные циклы failover/recovery, поведение после
перезагрузки и отсутствие утечек на реальном оборудовании ещё требуют отдельно
разрешённой проверки. При этой реализации роутер/VPS не изменялись.

## Состав образа и будущая приёмка

Образ включает flr-controller (Go 1.26.8, статический Linux ARM64), LuCI FLR,
AmneziaWG 3.1, sing-box 1.14.2 musl, Xray 26.3.27, wstunnel 11.0.0 и nfqws2
из zapret2 1.0.5.2. Архивы закреплены URL и SHA256; SDK сверяет ARM64 ELF,
ImageBuilder сверяет APK/ABI, подписи пакетов и точные хеши файлов rootfs.
Go formatting, race и vet должны пройти на том же опубликованном дереве исходников.

Первый запуск: служба контроллера запускает только администрирование и постоянный
LAN direct SOCKS5 (192.168.8.1:1080). VPN выключен, приватных профилей и настроек
нет. Временный direct SOCKS 1088 остаётся отдельным механизмом с собственными
ограничениями; retired flr-proxies не запускает движки. Сохраняется штатная
базовая сеть: LAN IPv6 RA/DHCPv6 выключены, WAN/учётные данные не задаются.

Экспериментальный direct bypass по умолчанию выключен. В LuCI можно явно выбрать
фиксированные TCP fake и QUIC fake (по два повторения) и включить эксперимент.
Прежде чем создать очередь 206, контроллер вызывает nfqws2 --dry-run и nft -c.
Включение требует уже работающего conntrack accounting (nf_conntrack_acct=1);
Это уже штатный default закреплённого OpenWrt 25.12.5
(/etc/sysctl.d/11-nf-conntrack.conf), который проверяется в rootfs. Контроллер
читает фактический флаг и не изменяет глобальный sysctl. Если администратор
позднее переопределил его на 0, эксперимент не активируется, direct остаётся
без очередей. Новые соединения
допускаются только через ограниченные наборы tuple (4096, 10 секунд); старые
установленные потоки не добавляются. При выключении/остановке удаляются только собственная таблица ip flr_bypass и
собственный дочерний процесс. Краш контроллера убивает дочерний процесс, очередь
с bypass не блокирует трафик без обработчика; при следующем запуске собственные
остаточные правила удаляются.

Обрабатываются только direct IPv4: класс маршрутизируемого direct 0x03000000 и
постоянный SOCKS 0x80400000, только первые шесть исходящих пакетов TCP 443 или
QUIC UDP 443. Трафик VPN, VPN bearer/probe, временного SOCKS 1088, ответы,
IPv6 и уже непрозрачные длительные соединения не попадают в очереди. Loop bit
0x00010000 не пересекает FLR masks; nfqws2 использует только low loop mask
0x00010000: его upstream фильтр
исключает пакет при совпадении любого бита, поэтому outer bit в mask исключил бы
и постоянный SOCKS. Сгенерированные пакеты с low bit получают 0x80010000
в собственной output route chain до обычных FLR output hooks; --bind-fix4
сохраняет WAN, а отдельный поздний output guard отбрасывает их на другом
выходном интерфейсе. Образ явно требует оба stock модуля kmod-nfnetlink-queue
и kmod-nft-queue, сверяет их версии и ARM64/kernel vermagic. Стандартные
upstream marks 0x40000000/0x20000000 не
используются. Пользовательские Lua, argv, пути и произвольные UDP-порты не
принимаются.

Пресеты не являются обещанием работающего обхода у конкретного провайдера.
YouTube, Discord voice и Telegram direct требуют отдельной разрешённой проверки
после загрузки на устройство: доступ/качество, TCP и QUIC, UDP ASSOCIATE,
исключение VPN, отсутствие регрессии игр и откат. Discord voice и произвольный
Telegram UDP не покрываются фиксированным UDP 443. Статические проверки образа
не доказывают загрузку, native fw4/NFQUEUE, восстановление или ISP-совместимость.

В metadata и verification остаются false: router_contacted, boot_runtime_tested,
recovery_tested, isp_bypass_tested. До отдельного разрешённого этапа проверки
GL-MT6000, резервной копии и восстановления этот образ не загружается и не
прошивается. Публикация CI-артефакта также не означает аппаратную приёмку.


## Доработки перед проверкой на устройстве (2026-10-05)

180-секундное окно принятия активации использует Linux CLOCK_BOOTTIME:
общее для CLI-процессов время с загрузки, включающее сон. Перевод календарных
часов не сокращает и не продлевает окно. Маркер `b1` хранит загрузку, поколение
и deadline в наносекундах; прежние маркеры календарного времени восстанавливаются
консервативно. Ошибка часов запрещает вооружение/подтверждение, а истечение или
startup выполняют восстановление; неудача сохраняет приватный маркер для повтора.

Чтение старых настроек нормализует пустые TCP/QUIC-пресеты в `off`, сохраняя
включённость и другой допустимый пресет. Старые ASCII-группы 81–128 байт остаются
без изменений при чтении и несвязанных правках. Чтение не переписывает файлы.
Новое явно переданное значение группы ограничено 80 UTF-8 байт, даже если оно
равно прежнему; пустое значение очищает группу. LuCI при сохранении порядка
семейств пропускает неизменённую группу, в том числе `[redacted]`, и проверяет
только явную правку. Приватные значения не раскрываются. Новые bypass-объекты
по-прежнему требуют полный набор полей и пресеты `off|fake`.

Эти изменения требуют проверки точных исходников в CI и новой сборки образа.
Они не означают аппаратную, загрузочную или ISP-приёмку.

## Сохранение обновлений и native recovery

Пакет теперь содержит явный keep.d из десяти долговечных FLR-файлов.
Первое обновление со старого образа требует отдельно сформированного и
проверенного архива: keep.d нового образа не влияет на старую прошивку.
[Runbook сохранения, firmware recovery и приёмки](RECOVERY-0.6.ru.md) содержит
точные пути, offline preflight и команды только для будущего разрешённого
этапа на устройстве. Приватные архивы и credentials в git не добавляются.

Короткие native-операции имеют отдельные пределы: 2 секунды для ip/uci/
conntrack и обычных команд; 10 секунд для nft и проверки sing-box; 30 секунд
для ubus и фиксированных init/rollback-команд. Stdout ограничен 64 KiB,
stderr — 4 KiB. Превышение — ошибка; обрезанные снимки не принимаются.
Отмена завершает process group, ожидание закрытия унаследованных pipes
ограничено ещё 250 мс. Обёртка сохраняет причину deadline/cancellation и
обычный exit status. Conntrack exit 1 считается пустым результатом только
с точной нулевой сводкой conntrack-tools; timeout, переполнение и иной stderr
не маскируются под отсутствие соединений.

Это пределы **одного subprocess**. Составная операция последовательно
суммирует их: например, восемь conntrack-очисток устройства могут занять
до 16 секунд плюс cleanup; restore включает несколько reload по 30 секунд.
Они не являются четырёхсекундным бюджетом transport probe. Запуск долгоживущих
engine-процессов и существующие probe contexts остаются отдельным механизмом.
При частичном сбое restore остаются recovery markers и исходник boot guard;
его nft table удерживается до завершения reload. Реальные kernel/native
тайминги, preserved sysupgrade, recovery и домашняя приёмка ещё UNTESTED.
