# Архитектура домашнего VPN для Flint 2

Дата исходного документа: 2026-09-29. Это историческая спецификация согласованной архитектуры. Документ сохранён как обзор замысла; актуальное состояние смотрите в [AGENTS.md](../AGENTS.md), [ROUTER-0.6.ru.md](ROUTER-0.6.ru.md) и [RUNTIME.ru.md](RUNTIME.ru.md). Исторические замечания о неразвёрнутом сервере ниже относятся к моменту написания документа.

Это отдельный проект роутера и отдельная серверная конфигурация. Проект выведен из более ранних проектов владельца как источников опыта; их код, инфраструктура и управляющие сервисы не являются зависимостями. Этот документ не означает, что прошивка уже собрана, программы установлены или соединения проверены.

## 1. Подтверждённые требования

- Роутер GL.iNet Flint 2 / GL-MT6000, постоянный VPN для домашней сети.
- Сохранить штатный U-Boot и его Web Recovery, позволяющий восстановиться без программатора.
- Основной канал — AmneziaWG 3.1; дополнительный — Hysteria2 с Gecko; обязательная поддержка VLESS.
- SS2022 + ShadowTLS v3 — подтверждённый будущий целевой профиль.
- Передавать TCP и UDP. Приоритет — стабильность, низкие потери и задержка в играх.
- Игры автоматически переключаются с AWG на Hysteria2 Gecko. VLESS для игр включается вручную — ответ пользователя от 2026-09-29.
- Предусмотреть direct-исключения на уровне сети, устройства и приложения.
- Списки маршрутизации не входят в публичный репозиторий: владелец подключает их приватным overlay (`policy/README.md`).
- Сервисы, которые должны идти через VPN или напрямую, задаются приватным overlay; без него всё, кроме локальных адресов, идёт через VPN.
- Основной DNS проходит внутри VPN и не зависит от доступности публичных DoH/DoT по WAN; bootstrap endpoint не требует работающего внешнего DNS.
- zapret2 от bol-van допустим как отдельный дополнительный механизм. Игровые соединения исключаются из его обработки.
- Основной собственный VPS выбирается владельцем; требования: статический IPv4, безлимитный трафик, стабильная задержка до домашней линии.
- Объём трафика без месячной квоты; численная FUP по средней скорости/CPU должна быть раскрыта провайдером отдельно.
- Задержки и доступность измеряются с домашней линии без VPN; при смене сети проверяются заново.

## 2. Выбранный подход и альтернативы

Рекомендуется гибрид: AWG как интерфейс ядра, sing-box как движок Hysteria2/VLESS и локальных прокси, отдельный контроллер политики поверх netifd/firewall4/nftables.

Вариант с пропуском всех соединений через один userspace TUN упрощает единое управление, но добавляет обработку основному каналу. Вариант из полностью независимых VPN-скриптов упрощает отдельные протоколы, но создаёт конкурирующих владельцев маршрутов и firewall. Гибрид сохраняет прямой путь через ядро для AWG и одного владельца политики.

Приложение на роутере — пакеты OpenWrt и модуль LuCI с воспроизводимой сборкой прошивки. Публичный коммерческий VPN, биллинг, Telegram-бот и многоузловая цепочка не входят в первую реализацию домашней системы.

## 3. Прошивка и совместимость

Отправная версия — [OpenWrt 25.12.5](https://github.com/openwrt/openwrt/releases/tag/v25.12.5), отмеченная upstream как latest на дату проверки. Target — mediatek/filogic, профиль glinet_gl-mt6000. Обновление версии является отдельным проверяемым изменением; сборки не следуют автоматически за latest.

AWG интегрируется из исходников: модуль ядра, tools, поддержка netifd и LuCI должны быть согласованы. [2Grey/awg-openwrt](https://github.com/2Grey/awg-openwrt/blob/master/README.en.md) публикует стек AWG 3.1 и поддержку OpenWrt 25.12.5; это общественная интеграция, а не основание обещать работоспособность произвольного бинарного kmod. Совпадение target, kernel ABI и всех параметров AWG проверяется при сборке и на устройстве. Пакеты 25.12 имеют формат APK.

Штатный bootloader, его environment, заводские данные и калибровки не перезаписываются. Основной распространяемый образ — sysupgrade. Отдельно проверяются содержимое образа, путь обновления GL-MT6000 и инструкция восстановления с корректным образом. Фактическая работоспособность Web Recovery подтверждается на устройстве до принятия новой прошивки в постоянную эксплуатацию.

## 4. Каналы

| Канал | Назначение | Реализация | Политика игр |
|---|---|---|---|
| AWG 3.1 | Основной маршрут | Интерфейс ядра Linux, маршрутизация IP | Первый выбор |
| Hysteria2 Gecko | Резервный UDP-транспорт | sing-box на роутере, upstream Hysteria2 на VPS | Автоматический резерв |
| VLESS + REALITY, RAW/TCP | Резерв при недоступности UDP, совместимость клиентов | sing-box на роутере, Xray на VPS | Только вручную |

Каналы параллельные. Hysteria2 и VLESS не вкладываются внутрь AWG. Внешние соединения каждого движка имеют отдельную WAN-марку и явный маршрут до VPS, чтобы не попадать обратно в собственный туннель.

[AWG 3.1](https://docs.amnezia.org/documentation/amnezia-wg/) сохраняет криптографическую основу WireGuard и добавляет механизмы маскировки. Параметры маскировки, padding и MTU должны быть согласованы на обеих сторонах; максимальная интенсивность маскировки не назначается без проверки потерь, PPS и задержки.

[Gecko](https://hy2.app/docs/advanced/Full-Client-Config/#obfuscation) дополняет Salamander фрагментацией и padding QUIC handshake; upstream обозначает его experimental. Поддержка существует в [стабильном sing-box 1.14.2](https://github.com/SagerNet/sing-box/blob/v1.14.2/docs/configuration/outbound/hysteria2.md), поэтому alpha-ветка ради Gecko не требуется. Отправная версия сервера — [Hysteria2 2.12.3](https://github.com/HyNetworks/hysteria/releases/tag/app/v2.12.3). Эти версии — кандидаты для совместных испытаний, а не уже проверенная пара. TLS-проверка сертификата обязательна. Начальная настройка congestion control — BBR без выдуманного значения доступной полосы.

Для VLESS фиксируются REALITY и RAW/TCP. [sing-box поддерживает TCP/UDP и XUDP](https://sing-box.sagernet.org/configuration/outbound/vless/). Оптимизация Vision включается только после проверки совместимости и передачи UDP, включая UDP/443: [Xray документирует особое поведение Vision для QUIC](https://xtls.github.io/en/config/outbounds/vless.html). Поле `network: tcp` из примеров не переносится как ограничение полезного трафика. Внешний TCP-транспорт делает UDP чувствительным к потерям и повторной передаче TCP, поэтому этот канал исключён из автоматической цепочки игр.

Полное IP-туннелирование AWG и проксирование TCP/UDP в двух резервных каналах имеют разную семантику. Передача произвольных IP-протоколов, ICMP и входящих соединений через прокси не обещается.

SS2022 + ShadowTLS v3 закреплён как будущий целевой профиль. Для него предусматривается отдельный adapter, импорт/экспорт профиля, проверки готовности и клиент-серверной совместимости. Сначала он добавляется как выбираемый вручную альтернативный профиль; включение в автоматическую цепочку требует отдельных испытаний. Нативный UDP Shadowsocks и его передача через TCP-обёртку — разные пути: режим передачи UDP и его ограничения будут определены и проверены при реализации. Из автоматической игровой цепочки этот профиль исключён.

## 5. Роутер: границы модулей

- **Policy controller:** хранит единую декларативную конфигурацию, рассчитывает маршруты и переключение, владеет nftables/ip rule. Он применяет изменения атомарно и откатывает невалидную конфигурацию.
- **AWG adapter:** управляет интерфейсом через netifd и публикует состояние; не меняет общую политику самостоятельно.
- **Proxy adapter:** управляет sing-box TUN, Hysteria2/VLESS и локальными LAN-прокси. Его auto-route не конкурирует с центральным контроллером.
- **DNS/classifier:** обслуживает LAN DNS, изолированные WAN/VPN views и nft sets. Правила имеют явный приоритет и TTL; resolver failover/перезагрузка DNS worker не перезапускают игровой dataplane.
- **Health supervisor:** проверяет реальную передачу через каждый канал; отдаёт результаты контроллеру и не переписывает firewall.
- **zapret adapter:** управляет только своим процессом и разрешённой веткой NFQUEUE. Отказ этого модуля не изменяет маршруты VPN.
- **LuCI UI:** позволяет выбирать режимы, исключения, ручной канал, видеть причины переключений и выгружать диагностику без секретов.

Hysteria2 и VLESS на роутере используют общий процесс sing-box в начальной реализации: его отказ затронет оба резервных канала, но не интерфейс AWG. Разделение на два процесса возможно после оценки памяти и необходимости изоляции; разные транспорты не считаются независимыми от общего runtime.

## 6. Маршрутизация

| Класс | Основной путь | При отказе | zapret2 |
|---|---|---|---|
| Локальные адреса и управление | LAN | LAN | Выключен |
| DIRECT: пользовательские исключения (overlay) | WAN | WAN при живом провайдере | Выключен |
| Широкий direct из overlay (режим split) | WAN | WAN при живом провайдере | Выключен |
| Игровой профиль | AWG | Hysteria2 Gecko; VLESS вручную | Выключен |
| Сервисы, закреплённые за VPN (overlay) | AWG | Hysteria2 Gecko → VLESS/REALITY; игровой вход сохраняет игровую цепочку | Выключен |
| Временная браузерная direct-сессия (например, для оплаты) | WAN, после явного включения | Ошибка без скрытой смены IP; сессия закрывается по deadline | Выключен; отдельный direct+DPI эксперимент допустим |
| Обычный VPN-трафик | AWG | Hysteria2 Gecko → VLESS/REALITY | Выключен |
| DIRECT + DPI для выбранных сайтов | WAN через zapret2 | WAN без обработки, либо блокировка по явному правилу пользователя | Выборочный профиль |

Порядок правил: локальные адреса → внешние сокеты VPN и служебные запросы → явные пользовательские override/прокси → обязательные VPN-назначения → банковские/direct-исключения → игровой профиль → сервисный VPN → direct+DPI → широкий RU/BY direct → основной VPN. Широкие географические/IP-правила не перекрывают игровой класс и обязательный/сервисный VPN. Приоритет банковского direct сохраняется и для игрового устройства.

Игровой профиль определяется надёжно: по устройству/выделенному VLAN/SSID или по явно проверенным назначениям. Универсальная эвристика по номеру UDP-порта не используется. Роутер не видит PID приложений на удалённом компьютере; выбор по приложению осуществляется через локальный клиент или явный прокси.

Для Firefox/FoxyProxy на LAN доступен отдельный SOCKS5/HTTP listener, исходящие подключения и DNS которого закреплены за WAN. Он доступен только разрешённым LAN-клиентам и не публикуется в интернете. Опция браузера «без прокси» сама по себе не обходит VPN на роутере.

Для сервисов, которым нужен домашний IP (например, оплата), пользователь открывает отдельный временный direct-профиль браузера, все web-запросы которого и DNS направляются в домашний WAN. Начальный TTL — 15 минут. Это отдельный listener/session, а не глобальное переключение сервиса или всего дома. Deadline и перезапуск отзывают session credentials и закрывают только её соединения; ordinary browser продолжает использовать VPN.

Сопоставление доменов IP-адресам имеет ограничения: общий CDN-IP может принадлежать нескольким сайтам, а собственный DoH клиента обходить LAN DNS. Для точного выбора сайтов предпочтителен явный LAN direct-прокси. Широкие direct-правила задаёт приватный overlay. Игровые и обязательные VPN-исключения стоят выше этих списков.

Исходная основа маршрутизации хранится отдельно (приватно). UDP/443 не блокируется глобально, IP-checker домены переводятся в обязательный VPN, игровые платформы — в игровой класс; torrent/ad/telemetry правила не включаются автоматически.

При отказе всех разрешённых VPN-каналов VPN-класс блокируется. DIRECT и локальная сеть продолжают работать, пока работает WAN. Общий аварийный выход через WAN доступен только как явно включённый режим с понятным статусом в UI.

## 7. Переключение каналов

У игрового и общего профилей разные списки разрешённых каналов. Состояния каждого канала: healthy, suspect, down, recovering. Успех одного HTTPS-запроса и свежий handshake не считаются достаточной проверкой UDP.

Начальные, подлежащие испытаниям настройки: проверка каждые 5 секунд, исключение после 3 последовательных неудач, возврат кандидата после 60 секунд устойчивого успеха. Проверяются путь внутри AWG, UDP-запрос через конкретный выход и HTTPS до нескольких независимых назначений. Обычный UDP DNS probe подтверждает ограниченную UDP-доступность и не заменяет игровые испытания.

Отсутствие userspace-процесса для proxy-канала или интерфейса для AWG — немедленная неисправность; одиночный рост RTT — сигнал деградации, а не команда переключить весь дом. Health-запросы получают отдельные марки, чтобы всегда проверять нужный канал, даже когда он не выбран основным.

Здоровые существующие соединения сохраняют свой канал. Новый канал выбирается для новых соединений. При отказе старого транспорта существующим соединениям потребуется восстановление; бесшовная миграция TCP или игровой сессии не обещается, даже если публичный IP VPS остаётся прежним.

После восстановления AWG новые соединения возвращаются на него, действующие игры на исправном Hysteria2 принудительно не переносятся. Контроллер работает с затронутыми conntrack-марками; глобальное очищение conntrack всего дома не применяется.

## 8. zapret2

[zapret2](https://github.com/bol-van/zapret2) — программируемое противодействие DPI через nfqws2 и Lua-стратегии. Это отдельная обработка пакетов, а не универсальное усиление шифрования VPN. Рабочую стратегию можно выбрать только после испытаний на будущем провайдере.

Основное применение в этой архитектуре: отдельный режим DIRECT+DPI для разрешённых сайтов, которым нужен домашний IP и помощь против DPI. Какие сайты в него входят, решает приватный overlay.

Правила допуска в NFQUEUE сначала проверяют класс/марку соединения в ядре. Из очереди исключаются игры, LAN, управление роутером, внешние пакеты AWG и Hysteria2, а также обычный direct. Затем применяются разрешённые назначения и диапазоны начальных пакетов. Не включается широкая обработка всего UDP или всех соединений на 443.

В [config.default](https://github.com/bol-van/zapret2/blob/master/config.default) предусмотрены FILTER_MARK, отдельные марки против зацикливания и ограничения числа пакетов. Новая интеграция резервирует непересекающиеся биты для policy routing, conntrack-классов, probe и zapret2. Не используются одновременно два независимых набора init-скриптов, управляющих одной и той же политикой firewall.

При остановке процесса очередь должна пропускать пакеты; queue bypass сам по себе не гарантирует защиту от переполнения очереди. Отдельный watchdog снимает hook при перегрузке или зависании. Режим отказа меняет только обработку direct+DPI, а не выпускает VPN-трафик в WAN.

Flow offload и SQM проверяются совместно с NFQUEUE: обработанные соединения не должны обходить необходимый hook. Исключение игрового потока из очереди не исключает косвенного влияния нагрузки CPU на весь роутер, поэтому нагрузка и длина очереди также ограничиваются.

Дополнительная обработка начального TCP-handshake VLESS через zapret2 допускается лишь как отдельный выключенный по умолчанию эксперимент после выявленной проблемы. Она не является частью базовой цепочки и не должна затрагивать игровой профиль. Gecko и AWG дополнительно через zapret2 не обрабатываются.

## 9. Сервер и доступность

Первый сервер — собственный VPS, независимый от прочих проектов владельца. Три транспорта работают как отдельные сервисы: AWG/kernel, Hysteria2, Xray. У каждого отдельная конфигурация, учётные данные и supervisor; их остановка не перезапускает другие сервисы.

Первая эксплуатационная цель — один Flint 2 и вся домашняя сеть за ним. Один AWG peer роутера не означает одно пользовательское соединение: нагрузка определяется суммарным трафиком, количеством TCP/UDP-сессий и пакетов всех устройств. Протоколы сервера допускают отдельные профили других собственных устройств; их управление и лимиты добавляются по отдельной потребности. Публичный многопользовательский сервис в первую реализацию не входит.

Начальный ресурсный ориентир постоянного узла — 2 vCPU, 4 GB RAM, 20–40 GB SSD/NVMe, порт 1 Gbps, статический IPv4 и безлимитный объём трафика. Это инженерная отправная конфигурация, а не подтверждённый throughput. Для целевого гигабита, Hysteria2 под длительной нагрузкой или нескольких активно используемых сетей отдельно оценивается 4 vCPU; проверяются мощность одного ядра, steal, UDP drops и задержка при загрузке. RAM/SSD сверх этого обычно менее приоритетны, чем CPU и сеть при текущем составе сервисов.

Основной канал, резервные транспорты и проверки готовности не утраивают автоматически весь пользовательский трафик: каждое соединение использует выбранный путь. На VPS сохраняется запас для одновременных потоков разных классов и переключения. Совместная проверка Flint 2/VPS обязательна: скорость штатного WireGuard не переносится на AWG/Hysteria2, SQM и zapret2 без испытаний.

Начальная схема публичных портов: AWG — отдельный UDP-порт; Hysteria2 Gecko — UDP/443; VLESS/REALITY — TCP/443. TCP/443 и UDP/443 не конфликтуют. Это проект распределения портов, а не обещание маскировки под полноценный HTTP/3: включённый Gecko несовместим с обычным QUIC сервером.

AWG требует маршрутизации/NAT на хосте, прокси самостоятельно создают исходящие подключения. Хостовый firewall явно разделяет эти пути. Управляющие интерфейсы не публикуются в WAN. Политики IPv6, DNS и служебного выхода сервера задаются явно.

Версии и контрольные суммы движков фиксируются. Обновление проходит validation, сохранение предыдущих конфигураций, проверку готовности и откат. Автоматическое подтягивание latest при старте исключается. Тонкая серверная конфигурация заменяет перенос внешнего control plane.

Три протокола на одном IP дают резерв по протоколу. Они не спасают от отказа VPS, блокировки его IP или сбоя хостера. Архитектура предусматривает второй независимый endpoint у другого хостера с проверкой ASN/аплинков; его аренда и включение являются отдельным следующим этапом.

После появления домашнего подключения сравниваются реальные маршруты, потери, p95/p99 RTT, вечерняя нагрузка и игры через каждый канал. При выборе хостера подтверждаются доступность аккаунта и оплаты, комиссии, трафик/PPS и политика хостера. Конкретный IP отдельно проверяется на captcha и возможность замены. Низкая частота captcha не гарантируется названием хостера.

## 10. DNS, IPv6 и производительность

Начальная пара DNS: Cloudflare Standard (`1.1.1.1`, `1.0.0.1`) основной → Quad9 Unfiltered (`9.9.9.10`, `149.112.112.10`) резерв. Оба работают без контентных фильтров и ECS для production-запросов, с DNSSEC, по HTTP/2 DoH внутри VPN. Порядок уточняется после измерений от выбранного VPS. Для direct (если overlay его определяет) остаётся отдельный резолвер. Конкретные DNS-настройки владелец ведёт приватно.

Основной DNS — DoH внутри выбранного VPN, минимум у двух независимых операторов; endpoint адреса DoH заданы IP с отдельным TLS server name и обязательной проверкой сертификатов. Публичный DoH/DoT по WAN не требуется. В sing-box путь DNS задаётся явно: новый HTTPS DNS dialer по умолчанию direct, поэтому proxy route/final сам по себе недостаточен. VPS endpoint также задан IP, SNI/REALITY имя сохраняется отдельно; адрес обновляется через исправный VPN с сохранением последнего проверенного набора. Bootstrap времени не отключает проверку TLS.

Для известных direct-доменов DNS получает отдельный WAN resolver провайдера. Кеши VPN/WAN и временных direct-сессий изолированы, ответы привязываются к TTL/классу и не расширяют global direct sets. Клиентский UDP/TCP53 перехватывается DNS роутера с исключением его собственных upstream-сокетов. Собственный DoH клиента не расшифровывается, но может скрывать домены от классификатора.

Отказ резолвера переключает DNS upstream без сброса игры. При отказе всех VPN DNS класса VPN отвечает ошибкой и не уходит в ISP; LAN и известные direct-домены обслуживаются отдельно. Для ещё неразрешённого неизвестного домена нельзя гарантировать broad direct без VPN DNS.

В первой реализации IPv6 на LAN отключён до проверки маршрутизации и firewall всех каналов. Незаметный выход IPv6 в WAN запрещён. Полная поддержка IPv6 добавляется отдельным проверяемым изменением.

MTU проверяется для фактической AWG 3.1 конфигурации и каждого proxy TUN, включая дополнительный padding. Произвольное значение «1420 для всех» не принимается без проверки. SQM/CAKE оценивается при нагрузке WAN; при подтверждённом bufferbloat включается с измеренной полосой и проверкой нагрузки CPU.

Для Hysteria2 на сервере отдельно проверяются размеры UDP buffers, socket drops, softnet drops, MTU и vCPU steal. Настройки Linux фиксируются как конфигурация проекта и применяются только после измерений, без универсальных sysctl из случайного руководства.

## 11. Приёмка будущей реализации

1. Воспроизводимая сборка GL-MT6000; проверка APK и ABI AWG; образ не содержит действий записи bootloader/environment/калибровок.
2. Проверенная процедура восстановления штатным Web Recovery на устройстве.
3. TCP и UDP работают через все три канала; отдельно UDP/443, игровые пакеты и DNS. Отдельно проверяются сертификаты и несовместимые параметры.
4. AWG-путь проходит через ядро без обязательного sing-box TUN и NFQUEUE.
5. Завершение AWG приводит к автоматическому Hysteria2 для новых игровых соединений; VLESS не выбирается для них автоматически.
6. Для общего профиля недоступность UDP допускает VLESS/REALITY; отказ всего VPN не ломает direct и LAN и не вызывает скрытого WAN fallback.
7. Возврат AWG не обрывает действующее соединение на исправном резерве; переключения не колеблются при одиночных потерях.
8. Direct-исключения overlay и явный browser direct-прокси используют домашний выход; собственный DNS клиента и CDN не приводят к неожиданному расширению исключений.
9. Счётчики и трассировка подтверждают отсутствие игровых/AWG/Hysteria2 пакетов в NFQUEUE. Остановка/перегрузка zapret2 не рушит роутер.
10. Перезагрузка роутера/VPS, ошибка конфигурации, пропавший DNS и обновление с откатом отрабатываются без потери управления LAN.
11. Длительная нагрузка включает игру одновременно с загрузкой, статистику потерь и задержки, CPU/softirq/UDP drops. Численные показатели принимаются после замеров нового подключения.
12. Cold boot при недоступных public DoH/DoT и подмене UDP53 на WAN не мешает подключению по закреплённому endpoint IP; VPN DNS не выходит в ISP при отказе туннеля.
13. Переключение DNS resolver не перезапускает игровой dataplane; WAN/VPN caches и TTL mapping не смешиваются.
14. VPN-обязательные правила overlay имеют приоритет над direct; временная direct-сессия использует домашний IP и закрывает только свои соединения по deadline/перезапуску.
